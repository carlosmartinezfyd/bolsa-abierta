# Operación, evidencia y despliegue

## Qué se registra y qué queda pendiente

`data-state/operations.json` conserva exclusivamente metadatos de ejecución: identificador del run/intento, SHA, disparador, correlación de solicitud, inicio, fin, duración y estado, más las mismas medidas por fase `inventory`, `positions`, `vacancies` y `build`. No guarda comandos, variables de entorno, salida de procesos, excepciones, URLs nominales ni filas de personas. El envoltorio descarta stdout y stderr del proceso hijo; sus errores se expresan mediante códigos y resúmenes permitidos. Un proceso interrumpido conserva `running`, sin inventar un cierre satisfactorio.

La retención es de **30 días y como máximo 1.024 runs**. Los recuentos públicos corresponden a esa ventana retenida; `discarded_runs` deja visible lo retirado. La rama `data-state` mantiene el estado fuera de la retención de logs de Actions. Su historial Git conserva las versiones anteriores de estos metadatos; el límite se aplica al fichero vigente, no promete borrar el historial de Git.

El exportador publica `operations.public_summary`: recuentos por estado/fase, último run limitado, intervalos observados, duración de seguimiento y campos de evidencia aún pendiente. No publica el historial de runs completo. La lista de campos se reconstruye, por lo que añadir campos privados al fichero no los publica.

Un `position_sync` que sale con código **2** se registra como `pending_budget`; la generación previa sigue activa. El envoltorio devuelve ese mismo código. Posiciones sale con código **3** cuando publica o verifica originales revisados desde caché autenticada pero falla su comprobación en origen: se registra `partial`, se conserva la fecha de comprobación oficial y el job termina con fallo después de publicar diagnósticos. Los demás errores mantienen sus códigos reales. Después de vacantes, una lectura SQLite en modo solo lectura obtiene exclusivamente `freshness.status`: `partial` conserva el código real 0 del proceso pero registra la fase como `partial`. Un estado ausente, inválido o fallido se registra como `failed`. El workflow propaga ese estado permitido como metadato y termina con fallo después de publicar diagnósticos; no presenta una captura parcial como satisfactoria. El workflow conserva diagnósticos y publica la instantánea con cobertura explícita, y después falla el job si una fase falló. Solo el SQLite de estado y `runtime/artifacts` de vacantes validadas entran en Git; `runtime/private-artifacts` y los originales de posiciones/inventario en claro permanecen excluidos. Con `PRIVATE_ARCHIVE_KEY`, `position_sync --archive-dir saved-state/private-originals` restaura o guarda exclusivamente bundles AESGCM autenticados. La persistencia valida integridad, hashes y manifiesto completos antes de añadir ficheros `.baenc`; ignora PDFs/JSON en claro. Los límites son 100 bundles, 512 MiB cifrados y 100 PDF únicos/128 MiB en claro. Los recibos que autorizan la recuperación están autenticados dentro del bundle, no en un JSON público. Un fallo de validación de caché conserva los diagnósticos y deja explícitamente pendiente su persistencia. El borrado de artefactos antes públicos se incluye con `git add -u runtime/artifacts`, sin reescribir el historial.

Ejemplo local, sin datos personales:

```bash
export GITHUB_RUN_ID=123 GITHUB_RUN_ATTEMPT=1
python -m bolsa_abierta.operations --state .runtime/operations.json start
python -m bolsa_abierta.operations --state .runtime/operations.json run --phase build -- python -c 'print("diagnostic output suppressed")'
python -m bolsa_abierta.operations --state .runtime/operations.json finish --status success
python -m bolsa_abierta.operations --state .runtime/operations.json summary
```

## Seguimiento de 14 días: 672 ventanas nominales

El primer run inicia la recogida de metadatos. **No equivale a haber completado el ensayo de acceso, CPU o cadencia de Cloudflare.** `elapsed_nominal_windows` cuenta tiempo transcurrido desde ese comienzo; no cuenta intentos exitosos ni demuestra observaciones por fuente. Después de 14 días el estado pasa a `evaluation_pending`, nunca a una aceptación automática.

Los dispatch del Worker conservan `scheduled_time`, `clock_received_at`, `dispatch_at`, `trigger=worker_cron` y `request_id`. `scheduled_time` es el `scheduledTime` real del controlador, en ISO UTC. Para Actions nativo se deja nulo: una ejecución `schedule` no acredita el instante cron causal. Se muestran intervalos entre runs; la mediana de retraso programado se calcula únicamente para runs Worker con un tiempo real válido. No se reconstruyen supuestos disparos omitidos. La correlación de la solicitud pública mantiene el identificador exacto y la confirmación de la instantánea correspondiente.

Antes de evaluar el ensayo debe fijarse el conjunto de fuentes que superan el acceso inicial y conservarlo durante las 672 ventanas, sin excluir después las que fallen. La aceptación propuesta exige antigüedad del último éxito validado ≤60 minutos en al menos 95 % de los cortes de cada fuente de ese conjunto, CPU P95 del comprobador <8 ms y margen de presupuesto ≥30 %. Debe publicarse también cobertura total, incluidas las fuentes bloqueadas al inicio. Estos son objetivos; los campos de antigüedad, CPU y margen permanecen **nulos/pending** hasta tener observaciones y métricas de la cuenta. Los metadatos de fase no bastan para rellenarlos. Referencia: informe aprobado, sección 7.5.

El Cron Worker sigue desactivado por defecto (`CRON_ENABLED=false`). Su configuración opcional usa `17,47 * * * *` y un sondeo HEAD acotado, sin descargar originales. Solo un cambio comprobado solicita procesamiento. Al habilitarlo, configurar también la variable GitHub `WORKER_CRON_ENABLED=true` para desactivar el reloj nativo y evitar dos procesamientos programados. Hacer un dispatch manual de prueba y comprobar correlación y cuotas antes de esa conmutación. Para volver al reloj nativo, desactivar Cron Worker y cambiar `WORKER_CRON_ENABLED=false`; verificar el siguiente run. Las solicitudes públicas y el Cron comparten los límites de la pasarela. Los límites y retrasos de `schedule` están documentados por [GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## GitHub Pages y publicación de código

`refresh.yml` se ejecuta por schedule, dispatch y cambios de código/interfaz en `main`. Ese push reconstruye y despliega Pages desde el nuevo SHA. La concurrencia `official-source-publication` serializa las publicaciones. Los cuatro procesos quedan envueltos por el registro de fase, y se vuelve a exportar el resumen después de cerrar el run para que la instantánea contenga el estado final. Un fallo de captura no borra la generación validada ni cambia su fecha de éxito.

Se publica además `data/gateway-status.json`, con solo `freshness.request_id`, `status` y `last_attempt_at`. `completed` exige éxito de inventario, posiciones, vacantes y construcción; cualquier fase parcial, fallida, ausente o pendiente impide confirmar el cambio observado por el Cron. Esto permite confirmar la publicación sin cargar el snapshot grande ni depender de que un visitante consulte el progreso.

La medida del run termina tras construir la instantánea; no representa confirmación de despliegue de Pages ni latencia de caché. El resultado real de `deploy-pages` permanece en el job. Los tests de Python/Node se ejecutan antes de obtener fuentes; CI valida además los workflows con actionlint.

## Configuración de Cloudflare existente

La automatización opera exclusivamente el Worker **`bolsa-abierta-gateway`** y D1 **`bolsa-abierta-gateway`** existentes. No crea bases, Workers alternativos, recursos de pago ni habilita facturación. El objetivo actual es `https://bolsa-abierta-gateway.cmartinezmtez.workers.dev`.

| Configuración GitHub | Uso |
| --- | --- |
| Secreto `CLOUDFLARE_API_TOKEN` | Wrangler: acceso a versiones del Worker existente y ejecución D1. |
| Variable `CLOUDFLARE_ACCOUNT_ID` | Cuenta existente; se admite secreto con el mismo nombre como alternativa. |
| Variable `CLOUDFLARE_D1_DATABASE_ID` | UUID de la base existente; binding `DB`. |
| Secreto `POSITION_INGEST_TOKEN` | Credencial administrativa de al menos 40 caracteres, ya configurada también como secreto Worker; backfill contra la versión candidata. |
| Variable `CLOUDFLARE_MIGRATION_MAX_INDEX_WRITES` | Límite conservador por defecto de 70.000; se puede reducir para otros consumidores de la cuenta. Cada índice reserva sus filas más 100 unidades de margen contra el uso restante del día UTC D1. No requiere una autorización adicional. |
| Secreto `PRIVATE_ARCHIVE_KEY` | Clave AESGCM dedicada de 32 bytes, codificada en base64 canónico; permite recuperación y persistencia cifrada de originales revisados. Nunca se publica. |
| Variable `PUBLIC_API_BASE` | Origen público del Worker usado por Pages. |

Si faltan token/cuenta/base, el workflow deja **pending configuration**, sin mutación. Nunca imprime los valores. Si faltan permisos, soporte de URL de versión o credencial administrativa, deja pendiente la preparación/backfill y conserva producción. Un HTTP 429 deja **pending_budget** con cursor D1 reanudable y candidato sin promover.

El ledger de la aplicación usa el día UTC autoritativo de D1, asignaciones por reserva/día y el saldo legado conservado de forma monótona. Incluye trabajo aún pendiente durante su plazo de ejecución. Una reserva DDL caduca a la hora; un job tiene un máximo de 18 minutos y comprueba la vigencia de cada reserva antes de continuar. Si atraviesa medianoche, conserva el cargo completo en ambos días posibles. Si se liquida mucho después de caducar, mantiene el cargo en los días de origen/caducidad y solo una pequeña sobrecarga administrativa actual; no bloquea indefinidamente días futuros por trabajo que ya no puede continuar.

El límite de 70.000 deja un 30 % de la referencia de 100.000 escrituras diarias Free para la aplicación y operaciones no previstas, pero no es una lectura de cuotas de toda la cuenta: otros servicios pueden consumir ese margen. La variable permite reducir el límite antes de ampliar consumo. La aceptación de margen de presupuesto y CPU del ensayo permanece pendiente de métricas reales; no se habilita facturación para resolver una pausa.

## Preparar y reanudar automáticamente con continuidad

1. El push a `main`, dispatch `mode=prepare` o ejecución diaria a las 07:13 UTC valida tests y ejecuta `wrangler deploy --dry-run` con la base existente. La concurrencia compartida `official-source-publication` serializa los cambios de `data-state` con captura e intake. `gateway-deployment.json` conserva SHA, estado y motivo agregado. Si ese SHA ya se desplegó completamente, el run diario sale sin mutación.
2. Un bootstrap pequeño prepara el ledger. El plan separa los **ocho índices B-tree de tablas pobladas** del esquema de control, FTS vacío y triggers. El esquema de control se reserva primero con margen y el coste de metadatos/índices menores conocidos; no ejecuta los ocho índices grandes juntos. Las dos tablas auditadas exigen 103.772 entradas nuevas entre los ocho índices, por lo que requieren más de un día con el límite aplicado. Ninguna generación histórica se borra para encajar el trabajo.
3. Cada índice ausente obtiene una reserva atómica propia para sus filas más margen, con día UTC D1, saldo legado y reservas en curso. Solo entonces se crea. `sqlite_schema` acredita el progreso y la repetición omite índices existentes. Si el siguiente no cabe, se registra `pending_budget` y la ejecución diaria siguiente continúa automáticamente. No se exige SQL manual ni una nueva confirmación. Los límites de tiempo detienen la preparación sin perder lo creado; un índice individual mayor que el límite queda pendiente explícito en vez de ejecutarse sin presupuesto.
4. Cuando están listos esquema e índices, `wrangler versions list` confirma que existe el Worker antes de `wrangler versions upload --preview-alias reliability`. La carga no promociona producción. El workflow solo acepta la URL devuelta por Wrangler que coincida exactamente con `https://reliability-bolsa-abierta-gateway.cmartinezmtez.workers.dev`; nunca envía la credencial administrativa a URLs arbitrarias y rechaza redirecciones. Un error de permisos o de URL de versión deja producción intacta y un motivo pendiente.
5. La candidata utiliza **la D1 de producción intencionadamente**. Un POST autenticado a `/internal/positions`, `{"action":"index","id":"HASH_DE_GENERACION_ACTIVA"}`, procesa como máximo 40 filas por llamada, con checkpoint y ledger. Cada run limita el backfill a 80 lotes y 240 segundos; publica únicamente progreso agregado. Un HTTP 429 conserva `pending_budget`, el checkpoint y la producción anterior. La ejecución diaria retoma automáticamente tras disponer de presupuesto.
6. Después del backfill, la misma ejecución comprueba la **generación activa actual**, además de tablas, vista, leases y triggers de presupuesto/revisión/control requeridos. Solo un índice preparado y el esquema completo permiten `wrangler deploy` del SHA comprobado. Una generación activa pendiente mantiene producción intacta. Si no existe generación activa, el código puede desplegarse sin poblarla y sin declarar cobertura. `mode=promote` permite reintentar directamente esa comprobación después de una preparación completa.

La migración crea FTS vacío y sus triggers; **no declara completa la búsqueda de filas existentes** ni hace un rebuild masivo. El Worker anterior sigue sirviendo sus consultas hasta la promoción; la candidata no activa una generación diferente durante el backfill. La recuperación cifrada tampoco acredita una comprobación oficial reciente. Las URLs de versión son públicas cuando están habilitadas, pero la ingesta exige el secreto administrativo y mantiene las restricciones de consulta.

No confundir esta carga de versión con `wrangler preview`, destinado a entornos aislados. Las [URLs de versión](https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/) mantienen recursos existentes; la [comparación oficial](https://developers.cloudflare.com/workers/previews/compare-workflows/) documenta el uso intencionado de producción. Los comandos se verificaron en las referencias oficiales de [Wrangler Workers](https://developers.cloudflare.com/workers/wrangler/commands/workers/) y [Wrangler D1](https://developers.cloudflare.com/workers/wrangler/commands/d1/). La [API de consultas D1](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/) admite SQL separado por punto y coma en un batch; los [batches D1](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) son transacciones que abortan al fallar una sentencia.

## Volver atrás

Antes de promoción, conservar el ID de la versión actualmente desplegada mediante `wrangler deployments list --config gateway/wrangler.toml`. Si falla la candidata, detenerse: el Worker anterior continúa activo y las tablas aditivas permanecen. No borrar la D1, `position_active`, el ledger ni los checkpoints para eludir los límites.

Si falla después de promoción, volver a la versión anterior con `wrangler rollback VERSION_ID --config gateway/wrangler.toml`, verificar consultas y conservar esquema/generación. El rollback de código **no revierte D1**. Su compatibilidad depende de mantener bindings y recursos; véanse [rollbacks oficiales](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/). Si se revirtió el reloj, restablecer `WORKER_CRON_ENABLED=false` y verificar el siguiente schedule. Una recuperación de datos es una operación administrativa distinta: requiere un original restringido, hashes/recuentos y activación validada; no se sustituye por rollback de código.
